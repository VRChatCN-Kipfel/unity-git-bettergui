# M4 · 界面多语言（贡献框架设计稿）

> 状态：随 `Editor/I18n/` 的多语言框架一同落地（2026-10）
> 里程碑：M4「中文本地化」的前置框架
> 关联：[M4-IGNORE-TEMPLATES.md](M4-IGNORE-TEMPLATES.md)（同一套"贡献者丢文件"的思路）、[ROADMAP.md](../ROADMAP.md) 第 53 行

## 1. 目标

让**翻译**和**模板**走同一条路：外部贡献者丢一个文件就能加一门语言，不必改代码、不必提交构建。

这一轮交付的是**框架与渠道**；简体中文语言包由仓库自己按这套流程作为"第一个贡献"提交，
用来对渠道本身做一次真实的压力测试（文档够不够、格式会不会踩坑、校验反馈是否准确）。

## 2. 贡献者契约

一门语言 = `Editor/I18n/BuiltIn/` 下 **1 个必需文件 + 1 个可选文件**：

| 文件 | 必需 | 说明 |
|---|---|---|
| `<lang>.json` | ✅ | 扁平键值映射：键 = `I18n.Keys` 里的字符串，值 = 译文 |
| `<lang>.meta.json` | ⬜ | `nativeName`（自称）、`maintainers`（GitHub 用户名数组）、`order` |

```json
{
  "ui.window.title": "Git 增强界面",
  "ui.graph.loading": "加载中…"
}
```

```json
{
  "nativeName": "简体中文",
  "maintainers": ["your-github-handle"],
  "order": 10
}
```

`<lang>` 用 BCP-47 风格代码（`zh-CN`、`zh-TW`、`ja-JP`、`pt-BR`、`zh-Hans-CN`）：2–3 位 ASCII
字母语言码，可跟最多两段 2–8 位字母数字区域/变体码。它同时是文件名，所以空格、下划线、
路径分隔符一律拒绝。

### 2.1 硬规则：占位符

**约三成键带格式占位符**（如 `{0}`；当前 64/203，分母随界面增长，以 `I18nSmokeTest` 输出为准）。规则是：

- 占位符**索引集合必须与英文一致**，且**每个索引的格式说明符必须一致**（`{0:N0}` 的 `:N0` 不能丢）；
- **顺序自由**——目标语言可以按自己的语序重排 `{1} … {0}`。

不一致的条目不会被采用，而是**丢弃并回退英文**，同时在语言窗口里报告"被丢弃的键"。
这不是可选的严格性：`I18n.L(key, args)` 拿到占位符不匹配的文案会直接抛 `FormatException`，
那比"这句没翻译"严重得多。

### 2.2 术语与维护者

- 术语以 [I18n.cs](../Editor/I18n/I18n.cs#L10) 顶部的**术语定则表**为唯一依据
  （fetch → 提取、stage → 暂存、checkout → 检出、branch → 分支…），代码里不得另立译法。
- 一门语言一个**主维护者**（写进 `maintainers`）：翻译是整体一致性产物，多人同时改同一语言
  必然打架，而模板可以一人一个互不冲突。

## 3. 发现与合并（与 ignore 模板刻意的两处差异）

```
UserSettings/GitBetterGui/I18n/<lang>.json    ← 个人本地（不入版本控制），优先级最高
<工程根>/.gitui-i18n/<lang>.json              ← 项目内共享（可提交，团队统一术语）
<包>/Editor/I18n/BuiltIn/<lang>.json          ← 内置，优先级最低
```

差异一：**键级合并**，不是整份覆盖。语言包的天然单元是"一个键的文案"，所以个人只想改三条术语
时不必复制整份语言包；高优先级层提供多少键就覆盖多少键，其余继续用低层。

差异二：**允许部分翻译**。没提供的键回退英文，语言窗口显示覆盖率（`ja-JP 42/203`）。
"只翻了 20 个键"是一份有效贡献——这是让社区能起步的关键。

一个刻意设计的细节：若高层把某个键判为**无效**（占位符不一致），该键会从结果里**剔除**，
而不是让低层的旧译文静默顶上来。否则用户改错了译文却以为"改动没生效"，比直接回退英文更难排查。
低层自己的无效键同理。

## 4. 校验与防御（不信任输入）

| 情形 | 处理 |
|---|---|
| JSON 结构非法（尾逗号、重复键、非字符串值、尾随内容） | 文件级错误，该层整份不采用，并告警 |
| 文件名不是合法语言代码 | 文件级错误，不采用 |
| 键不在当前英文表里（旧包 / 手写错键） | 忽略该键并计入 `UnknownKeys`（界面显示条数） |
| 键以 `_` 开头 | 视为贡献者写的注释键，**静默**忽略（不算未知键） |
| 占位符不一致 | 丢弃该键、计入 `InvalidKeys`、运行时回退英文 |
| `<lang>.meta.json` 损坏 | 只降级元数据（回退用语言代码当显示名），不影响译文 |

扁平 JSON 由 `FlatJson` 自解析：Unity 的 `JsonUtility` 不支持任意键字典，而引入
Newtonsoft 会破坏本包"零依赖"约束（`package.json` 的 `dependencies` 为空）。
解析器**严格**：宁可报错，也不要把半个文件静默读成半门语言。

## 5. 运行时

| API | 语义 |
|---|---|
| `I18n.ApplyLanguage(lang)` | 先把键表整体恢复到英文基线，再叠加语言包译文；语言为空或找不到包 → 回到英文 |
| `I18n.SetLanguage(lang)` | 同上 + 写入 `EditorPrefs`（`kf.gitui.language`），跨会话记住 |
| `I18n.InitFromPreferences()` | 启动时恢复：优先已保存选择，否则按系统语言猜一门（没有包则自动回退英文，且不写盘） |
| `I18n.LanguageChanged` | 语言切换完成事件；界面必须订阅并重建 |

**"先恢复基线再叠加"是刻意的**：否则从 A 语言切到 B 语言时，A 语言独有的键会残留在界面上。

**UI 不可能自动换文案**：`GitWindow` 订阅 `LanguageChanged` → `RebuildUI()` + `ReloadHistory()`
（图谱表在 `BuildLayout` 里是新建的，必须重新灌数据），`OnDisable` 退订。

## 6. 骨架导出（贡献者的捷径）

语言窗口的 *Export skeleton for a new language…* 会往 `.gitui-i18n/` 写一份
包含**全部键 + 英文原文**的 `<lang>.json`（以及一份 meta 模板），贡献者只需替换值。
已有同名文件时**拒绝覆盖**——那是贡献者的成品。键序取自 `I18n.Keys` 常量的声明顺序
（靠 `MetadataToken` 排序稳定下来），保证骨架、覆盖率、文档三处的键序一致。

## 7. 验证

```bash
Unity -batchmode -nographics -projectPath <宿主项目> \
      -executeMethod KF.GitUI.I18nSmokeTest.Run
```

覆盖：键表三方一致（常量 / `AllKeys` / 英文表）、英文表占位符索引连续、
扁平 JSON（含六类非法输入必须抛错）、占位符比对（含"顺序自由"与"格式说明符不同必须拒绝"）、
语言代码校验（含 `../evil` 之类的路径穿越）、单文件解析与三类诊断、键级归并与"高层无效键剔除"、
`ApplyLanguage`（部分翻译回退 / 找不到包 / 切换无残留）、骨架导出与拒绝覆盖、
`ui.language.*` 键的双向完备性。

## 8. 已知边界

- **菜单路径不可本地化**：`[MenuItem("Window/Git/…")]` 的路径由 Unity 静态解析，只能在代码里写死
  （[I18n.cs](../Editor/I18n/I18n.cs#L18) 已注明）。所以"中文界面完整"的验收边界是**窗口内文案**，
  菜单项路径保持英文。窗口标题、按钮、提示、对话框全部可本地化。
- **RTL 未验证**：阿拉伯语/希伯来语需要的镜像布局没有做过验证，先不宣称支持。
- **翻译平台未接**：没有对接 Crowdin 之类的工具链；当前只支持"人改 JSON"这一条路径。
- **覆盖率只统计键数**，不区分"译文质量"。
